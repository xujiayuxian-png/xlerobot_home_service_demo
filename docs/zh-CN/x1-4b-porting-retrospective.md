# 在 X1 上运行 4B 视觉语言模型：适配总结与展望

更新日期：2026-09-16。本文是可供公开分享的阶段总结，记录一次机器人端侧多模态部署实践。模型、运行时版本和数字均对应本次实验，不代表其他设备或后续版本。

**我们已经在 X1 的原生 Ubuntu 22.04 上跑通 Qwen3-VL-4B 的本地推理，接入机器人接口，并完成小样本功能与多模型共存验证；但首次完整实机任务在物品识别阶段发生原生推理进程退出，尚未完成稳定的取物递送验收。**

这项工作的价值，是打通并验证了一条具体的端侧部署路径，同时暴露了从“能加载模型”到“能可靠服务机器人”之间的差距。

## 1. 为什么做这件事

项目原本通过机器人电脑和远程 GPU 服务协作，完成语音取物、导航、抓取和递送。X1 适配的目标是用机器人本机承接这些工作，减少对外部电脑、网络和 GPU 服务器的依赖。

4B 模型在这里承担三个低频但关键的任务：理解开放取物指令、在头部图像中定位目标、在腕部图像中判断抓取状态。ACT 负责生成抓取动作，人员检测和语音转写由独立模型承担。机器人控制命令仍由本地控制系统执行，VLM 不直接控制电机。

从 3B 探索到 4B，并非单纯追求参数规模。此前小物体漏检、框偏移和抓取判断错误已经影响演示，希望通过新的模型路径改善这些能力。不过，参数更大不能保证转换后的端侧模型更好，运行链路是否正确同样重要。

## 2. 第一条路线：加载成功，识别却退化

最初采用厂商提供的 4B 转换包及 AidLite/AidGen 运行链路。接口可以返回结果，但头部画面中羽毛球与蓝色打火机的框明显偏离目标。

我们没有立即修改坐标补偿，而是逐层缩小排查范围：

1. 固定同一张图、同样的 448×448 输入、提示词和 0–1000 坐标约定。
2. 绕过 HTTP 和机器人客户端，直接调用 SDK。
3. 对照新旧视觉运行库及厂商默认生成线程配置。
4. 用 GPU 上的同系列 4B 模型作离线参考。
5. 检查视觉输出、语言模型输入及示例代码中的特征传递。

直接 SDK 与 HTTP 路径产生相同的偏框；GPU 对照在相同输入尺寸下框住了目标。这使排查重点从机器人坐标换算转向了转换包和多模态执行链路。GPU 只用于诊断，没有成为新部署的运行依赖；两边量化不同，也不能视为严格的单变量精度对照。

进一步检查发现，已枚举的 raw 包接口和厂商示例链路没有传递 Qwen3-VL 所需的三路 DeepStack 中间视觉特征。完整 AIDEM 视觉模型也只有一份主特征输出，但其语言模型内部采用专用封装，未被完整解析。

因此，**DeepStack 特征链路存在明确的兼容疑点，但不能断言它是全部误差的唯一原因**。本次没有完成逐层数值对齐或 DeepStack 消融，位置编码、量化及其他实现差异仍可能影响结果。

详细对照见[识别退化诊断](x1-qwen3-vl-4b-diagnosis.md)。

## 3. 第二条路线：GenieX、GGUF 与 Hexagon

我们转向 GenieX 提供的 GGUF/Hexagon 路线，而不是继续在已有转换包外围修补。当前适配不是重新导出了一套 QAIRT 模型，也不是从头实现了 NPU 推理引擎。

| 项目 | 本次验证配置 |
|---|---|
| 设备 | X1，QCS8550 / Hexagon v73 |
| 系统 | 原生 Ubuntu 22.04，ARM64，无容器 |
| 模型 | Qwen3-VL-4B-Instruct，GGUF Q4_0 主权重、F16 视觉文件 |
| 运行时 | GenieX 0.6.1，`llama_cpp:HTP0` |
| 推理设置 | 上下文 2048，CPU 辅助线程 2 |
| 图像 | 保持原比例，640×480 以内，PNG，不上采样 |
| 服务方式 | 一个常驻模型，共用意图、定位和抓取判断接口 |

### 跨过 Ubuntu 22.04 的运行库门槛

这一版原生运行库需要 `GLIBC_2.39` 和 `GLIBCXX_3.4.32`，无法直接在当前系统环境加载。我们把所需 Ubuntu 运行库解包到独立目录，通过专用动态加载器启动 VLM Python 环境，没有替换系统 libc，也没有升级整个机器人系统。

这条路径实际初始化了 v73 DSP 会话，随后完成模型推理。它解决了本机实验的兼容障碍，但仍是需要固定依赖、进一步整理安装流程的工程方案，不能认为复制一个 Python 环境就能在任意 Ubuntu 22.04 设备复现。

### 确认计算实际运行在哪里

日志显示 37/37 层卸载到 HTP0，视觉文件包含第 5、11、17 层的 DeepStack 投影权重。视觉编码也选择 HTP0，但不支持的 UPSCALE 算子存在 CPU 协作。

准确说法是：**本机 CPU 与 NPU 协同推理，无远程 GPU 依赖。** 不应宣传为全部算子纯 NPU。日志中的通用“offloaded to GPU”措辞也不能脱离实际设备 HTP0 来解读。

## 4. 真正影响结果的适配细节

### 图像处理要用真实目标验证

同一场景中，448×448 输入仍漏掉了小打火机，保留 640×480 后检测成功；JPEG 与 PNG 的结果也出现差异。最终选择原尺寸、原比例和 PNG。

这只是本次小目标样本上的有效选择，不是“PNG 必然比 JPEG 准确”的普遍结论。1280×960 上采样还触发过 DSP 队列错误并导致进程退出，因此没有把放大输入当作默认增强方案。

### 多次请求需要显式隔离状态

早期连续调用的第二次请求出现多模态生成失败。每次独立任务前重置模型会话后，连续检测恢复。服务因此采用串行推理、请求间重置、忙时明确拒绝的方式，避免共享状态和积压。

实机故障之后，又把模型加载、重置、生成和销毁固定到同一个常驻线程，并增加启动图像预热。它们是防护措施；目前没有证据证明跨线程调用就是原始崩溃根因。

### 抓取验证要问清楚物理关系

直接询问“是否抓取成功”曾把桌面上的胶棒误判为已抓起；过度强调分离的短提示又误伤了成功样本。最终改为区分三种位置关系：物体在夹爪口被带起、物体在桌面且与夹爪口分离、看不清。

这一视觉步骤检查是否带起物体，不承担第二次确认物品类别的全部责任；既有夹爪位置检查继续保留。两正两负样本通过，只说明这几个样本的行为改善，不能证明小物体与遮挡问题已解决。

### 模型速度必须和任务超时一起设计

图像推理约需 6～7 秒，失败后的新帧复核还需要第二次请求。原来父级 10 秒预算可能在第二次结果返回前终止任务。GenieX 路径改为单次请求 15 秒、父级验证 35 秒，以匹配现有复核逻辑。

这是对实际推理耗时的适配，不是提高模型速度；机器人控制频率没有因此降低。

## 5. 已经验证了什么

| 验证范围 | 实测结果 | 解释边界 |
|---|---|---|
| 意图理解 | 3 条开放取物指令解析正确；取消和含糊指令不误发取物任务 | 共 5 条，不代表全面语言能力 |
| 头部物品定位 | 羽毛球、蓝色打火机检出，框目视基本贴合 | 无人工真值框及 IoU 统计 |
| 腕部抓取判断 | 2 张已抓起、2 张未抓起均符合预期 | 使用历史图片，无实机成功率结论 |
| 四模型并发请求 | VLM、ACT、人员检测、Whisper 均返回 | ACT 动作未执行；人员样本为无人场景 |
| 服务软件测试 | 5 项通过 | 覆盖线程归属、状态隔离、输入约束等，不测试电机 |
| 完整实机任务 | 导航、转身和头部动作完成；识别阶段 VLM 进程退出 | 尚未通过完整递送验收 |

一次四模型共存检查中，VLM 检测约 6.13 秒，ACT 约 0.063 秒，人员检测约 0.085 秒，Whisper 转写约 1.25 秒。这些是单次调用耗时，不是长期吞吐或尾延迟。

四个推理服务常驻、未启动 ROS demo 的 20 秒采样中，整机 CPU 平均约 10.84%。首次实机运行记录中，包含启动和导航的窗口平均约 62.5%、峰值 100%。CPU 百分比均以全部在线核心总容量为 100%；这两个数字对应不同工况，不能相互替代，也不能据此声称完整 demo 只需约 11% CPU。

单独模型实验测得进程峰值 RSS 约 1,022,940 KiB，未计入全部 DSP 与共享内存，不能作为整个模型的内存需求。

详细参数、实验顺序和结果见[运行时实验记录](x1-qwen3-vl-4b-official-experiment.md)。

## 6. 尚未解决的问题

当前最优先的问题是原生推理进程的稳定性。首次实机识别时进程退出，监督进程随后停止整套 demo。没有发现 OOM 证据；原日志缺少退出码和原生调用栈，具体崩溃原因尚不明确。

之后在相机开启、四模型共存以及 systemd 环境下重放，未稳定复现。新增线程管理、预热与诊断后，11 个历史功能样例及并发请求再次通过，但不能据此宣布故障根治。

识别质量也没有完全解决：新鲜头部图像中的蓝色打火机仍出现过未检出或无效 JSON。进程稳定、输出格式正确、目标识别正确是三个不同问题，应分别记录和处理。

## 7. 后续路线：先让演示可靠，再优化部署

以下是建议的工作顺序，不是已经完成的能力。

| 阶段 | 具体工作 | 可交付结果 |
|---|---|---|
| 近期：复现原生退出 | 保存退出信号、故障输入和版本；必要时收集原生栈；对比单模型、共存及整机工况 | 能解释的故障原因和对应修复，或明确的触发条件 |
| 近期：完成实机闭环 | 在固定场景先完成一次取物递送，再少量重复，包含失败及取消；保存阶段耗时 | 可展示的完整运行记录，失败也计入结果 |
| 随后：改善小目标 | 保留少量固定回归图并增加未参与调参的新图；对照原图与有界裁剪，标注框以比较位置误差 | 能说明收益与代价的图像方案，避免只优化旧样本 |
| 随后：约束输出 | 评估运行时是否支持结构化生成；严格校验字段；有限重试与任务超时一起设计 | 减少无效 JSON，不靠改写答案制造成功 |
| 随后：降低等待 | 分解视觉编码、首 token、生成及排队耗时；缩短输出；按任务阶段协调 NPU 请求 | 可比较的阶段延迟和资源记录 |
| 发布前：整理复现 | 固定依赖和权重来源，提供配置模板、安装步骤、校验和、无电机自检与卸载方式 | 第三方可按说明运行的实验版本 |
| 更远期：深入 NPU 适配 | 评估兼容 Ubuntu 22.04 的运行时构建；研究保留 DeepStack/MRoPE 的导出与数值对齐 | 更易维护的运行库或经过验证的新转换路径 |

不必为了一个演示先建设庞大的评测平台。少量固定样本防止回归、少量新样本检查泛化，再加真实完整流程，通常比反复调整同一张图更有价值。

如果未来考虑让小模型承担部分意图或简单判别，应先测量常驻内存、切换成本和总体延迟。模型数量增加未必降低资源开销，当前共享一个常驻 4B 的方案仍有简化部署的价值。

## 8. 对外发布时如何表述

建议定位为：**“X1 / QCS8550 上 Qwen3-VL-4B 端侧部署的工程实践与阶段验证”**。

可以公开说明已经实现本机 CPU+NPU 推理、Ubuntu 22.04 隔离运行库适配、机器人服务接口接入，以及少量真实图像和多模型共存验证。当前不应宣称已经稳定完成自主取物递送、所有算子均在 NPU、任意物品识别可靠，或 DeepStack 已被证明是旧包退化的唯一原因。

推荐发布材料包括代码与版本清单、架构与部署说明、经筛选的原图和原始输出、成功及失败案例、测量口径，以及完整实机演示。运行库和权重说明其来源与适用许可；本次总结不代替对具体资产再分发条件的核对。机器凭据、私人录音、真实地图、标定和原始机器日志不随代码发布。

现阶段可用于项目介绍的摘要：

> 我们在 X1（QCS8550）的原生 Ubuntu 22.04 上探索了 Qwen3-VL-4B 的端侧部署，通过 GenieX 的 GGUF/Hexagon 路径实现本机 CPU 与 NPU 协同推理，并将意图理解、物品定位和抓取判断接入机器人服务。工作覆盖运行库隔离、模型状态管理、图像输入与超时适配，并完成小样本及多模型共存验证。首次实机测试仍暴露了原生推理退出问题，因此当前成果定位为可继续验证的工程原型，后续重点是稳定性、真实场景识别与可复现部署。

本项目的原创工作主要在部署适配、诊断实验和机器人系统集成；基础模型、推理引擎和硬件后端来自各自上游项目。公开分享时应保留这些归属，并把未解决的问题作为结果的一部分。

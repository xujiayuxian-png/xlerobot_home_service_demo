# X1 无人值守开发与离线验证记录

日期：2026-09-15；分支：`x1-native`；本轮修改前版本：`e85ad49`。

用户不在机器人旁边，本轮先确认没有正在执行的任务，然后停止 demo 服务。
没有重新启动硬件控制器，没有发起定位、导航、抓取、递送或语音任务。
本轮的“离线”指不运行实机动作；测试仍在 X1 的原生 Ubuntu / ROS 环境中执行。

## 1. 已实现：有就绪条件的分组启动

增加可独立回退的 `demo.staged_startup` 配置，经 `tools/run` 传给
`x1_staged_startup`。默认 `false`，只允许与 `demo.low_load: true` 一起使用。
当前机器未启用这个开关，保留上一轮实测过的启动方式。

| 阶段 | 启动内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| platform | 原有平台运行时、共享状态网关 | 准备姿态与底盘停止路径诊断正常，TF 查询服务已注册 |
| sensors | 雷达、D455、原生腕部相机、相机健康检查 | 头部彩色、深度、内参、腕部四项状态新鲜 |
| navigation_moveit | 现有导航各节点、MoveIt | 定位与定位运动生命周期组正常；IK、定位、命名地点导航、接近目标接口已注册 |
| perception | 物品识别、抓取验证、人员检测、ACT 适配器 | 对应动作接口已注册，人员检测模型实际预热成功 |
| application | 动作执行、抓取、递送、任务、固定播报、语音、网页 | 进入现有应用运行方式；任务与语音就绪仍分别判断 |

这使 YOLO 预热与语音模型初始化错开。导航和 MoveIt 仍在同一组并行启动，
本轮没有按固定 CPU 配额限流，也不能保证每个单独阶段都低于 60%。

每个有门槛的阶段使用一次性只读探针，最长等待 120 秒，就绪条件稳定至少 0.5 秒
才放行。诊断回调接收最新状态，就绪检查最多约 5 Hz，模型查询最多约 1 Hz。
探针不订阅图像、不发送动作目标、不调用控制服务，通过后退出，不增加待机常驻进程。

诊断同时检查消息时间戳与本机接收时间；相机还检查生产者报告的帧年龄。
旧状态、未来异常时间戳、无效年龄、缺失接口不能当作就绪。设备恢复后的新状态
可以重新通过检查。阶段超时、模型预热失败或探针非正常退出使 launch 失败并清理
其拥有的进程；正常停止不推进下一阶段，也不自动重启任务。

**接口注册不等于模型可用。** 人员检测增加 `/scan_for_person/model_ready` 只读查询，
区分加载中、预热成功、加载失败、后端禁用。查询不拿模型加载锁，不因长时间预热
而阻塞。仅检查既有预热完成事件，不重新加载或运行推理。

**启动完成不等于定位完成。** 不等待 `lifecycle_manager_navigation` 激活，也不等待
地图初始位姿，首次定位仍由现有任务逻辑触发。任务入口的定位与安全检查保留。
最后一组启动日志只表示应用已启动，不表示语音已能唤醒或整机已通过验收。
网页在最后一组才出现；前面各组的等待原因从 systemd / launch 日志查看，
整个启动过程仍可通过 `tools/run demo --stop` 停止。

## 2. 已实现：减少性能采样自身的开销

采样器仍每秒读取整机 CPU、进程 CPU/RSS/线程和控制器线程调度信息，保留原有
10 秒滚动窗口算法。变化是：

- 进程名称从已经读取的 `/proc/PID/stat` 中解析，省去逐进程再打开 `comm`。
- 温度、CPU 频率、内存总览和 CPU 压力改为约每 5 秒读取，缓存中间结果。
- 报告增加 `telemetry_age_s`，明确慢速遥测有多旧，不能将缓存温度当成逐秒实测。

上一轮两个同时运行的采样器本身消耗了可见 CPU。后续验收只保留一个采样器，
避免多份测量相互干扰；仍不从整机实测负载中直接扣除观察开销。

新旧对照条件：demo 停止、不开设备、无网页健康请求；旧版为 `e85ad49` 的采样脚本，
新版为本轮脚本。按旧、新交替顺序，各执行三次 60 秒，使用子进程自身
`getrusage` 的用户态与系统态 CPU 时间计算单核占用。对照期间不构建、不运行测试。
桌面与开发会话仍存在，因此整机后台负载只作背景记录，不作为 demo 性能收益。

| 采样器 | 三轮自身 CPU（单核百分比） | 三轮平均 |
| --- | --- | ---: |
| 原版 | 7.549 / 7.559 / 7.576 | 7.561% |
| 新版 | 4.148 / 4.119 / 4.089 | 4.119% |

自身 CPU 平均减少 **45.53%**。每轮均保存 60 个逐秒 CPU 样本，报告中的进程数量
范围为 578–583；结果包含 Python 进程启动与报告序列化的 CPU 开销。
这不是 demo 功能负载下降 45.53%，也不能用它倒推修正之前的 53.36% 待机实测。
运行完整 demo、额外查询网页健康状态时，仍需重新记录采样成本。

原始六份报告、脚本版本引用与 `getrusage` 汇总位于忽略目录
`.xlerobot/environment/profiler-comparison-20260915-110131/`，未提交机器日志。

## 3. 软件验证与已知边界

构建从 `ros2_ws` 执行，涉及 `xlerobot_bringup` 与 `xlerobot_perception`。
两包构建成功；本轮最终相关测试 **29 项通过**：bringup 的采样器、启动顺序与
完整启动契约共 24 项，人员检测运行时共 5 项。测试按包隔离执行，未打开电机设备。
软件测试覆盖：

- CPU 采样缓存不影响逐秒 CPU/进程更新，进程名称包含括号和空格仍能解析。
- 阶段缺失状态、旧帧、无效年龄、设备恢复、服务消失。
- 实际 launch 子进程的成功放行、失败不放行、中途停止与子进程清理。
- 独立 ROS 域中发布合成诊断、模拟模型查询，实际运行探针进程，验证加载中、
  成功、失败和超时；不包含任何硬件 launch。
- 四种语音/网页开关组合的完整启动图归组与参数序列化；构造图但不执行硬件节点。
- 人员模型预热状态契约与已有感知软件行为。

测试还用阻塞中的假模型持有加载锁，实际调用就绪服务，确认它能立即返回加载中，
释放预热后再返回成功；这避免启动探针被模型加载锁拖住。

测试暴露并修正了 Humble 的 ROS `byte` 诊断字段差异，以及 JSON 字符串被 launch
误当成 YAML 参数结构解析的问题。不能用只检查源码字符串的测试代替实际进程验证。

本轮不能验证分组启动的实机 CPU 峰值、真实相机与生命周期启动时序、声音效果、
导航与抓取成功率。之前的未定位待机 53.36% 数据不因此升级为完整 demo 的成绩。
30 分钟完整待机、1 小时混合任务和至少 10 轮取物递送仍待有人在场时完成。

## 4. 有人到场后的最小验证流程

1. 先保持 `demo.staged_startup: false`，用当前版本测三轮原启动基线。
2. 停止服务，在忽略的 `config/local.yaml` 中将 `demo.staged_startup` 设为 `true`，
   准备两个终端。
3. 先在终端 A 使用单个 `tools/doctor robot --profile --duration 180 --label staged-startup`
   开始采样，再在终端 B 用 `tools/run demo --hardware` 启动，观察准备姿态、相机、
   模型、网页与语音状态。待机另外采样；同工况重复三轮，记录总启动时长、最高
   10 秒负载与错误。若启动超过 180 秒，应加长采样，确保覆盖整个过程。
4. 做唤醒、开放指令、完整任务与取消回归。延迟过大、阶段超时或新增功能失败时，
   先停止，将 `demo.staged_startup` 改回 `false`，再显式启动。

两个版本都须在相同温度、相机配置和开发后台条件下比较。不要把“等待更久”本身
当作成功，也不要把初始化开销挪到第一次抓取后宣称启动优化完成。

后续可继续无人值守的方向是合成数据回放、图像时间戳与资源释放故障注入、固定音频
格式检查、性能日志分析。相机生产者诊断和 Nav2 组合仍先做独立验证；NPU 留作后续专题。

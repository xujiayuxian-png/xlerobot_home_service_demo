# X1 优化复盘与后续路线

日期：2026-09-15。范围：这台两轮 XLeRobot 的 Ubuntu 22.04 原生 demo，
源码分支 `x1-native`。本文总结已经得到的证据，并给出下一阶段建议；建议部分尚未实施。
具体实现与原始数据位置见[第一阶段实现记录](x1-native-implementation.md)，
目标约束见[完整 demo 低于 60% 的方案](x1-demo-under-60-plan.md)。

后续进展：已完成一轮[本机 NPU 离线探索](x1-npu-experiments.md)，人员检测与中文
短指令转写已在 HTP 上运行。独立模型数据不改变本文的整机基线，生产配置尚未切换。

## 1. 对“20% 的时间取得 80% 的效果”的判断

作为对投入产出的判断，我基本同意：这一轮找到了几个重复执行、容易隔离验证的大热点，
一次结构调整就取得明显收益。后续工作更容易涉及多个模块的时序、消息传输、调度和故障恢复，
验证成本会明显增加。我们没有完整的工时和理想上限数据，不能把 20/80 当成已测得的比例。

“80 分”可以理解为第一轮架构调整的进展。对完整演示的可靠性，还缺少任务期间和长时间
运行的证据：当前测到的是**未定位待机**，不是已经连续成功完成抓取递送的满分系统。

现阶段不宜以“剩下只差几个 CPU 百分点”来规划工作。待机最高滚动 10 秒为 54.93%，
距离 60% 约有 5.07 个百分点；ASR、完整导航、ACT 观察处理和人员检测各需要多少增量，
还没有逐阶段测清。这 5 个百分点也不是可以无条件分配给新功能的安全余量。

下一阶段的价值应优先体现在：启动可预测、任务不失守、失败能停下、重复演示结果稳定。
若这些已满足，再判断进一步降低待机是否值得增加维护复杂度。

## 2. 本次真正证明了什么

| 测量 | 优化前 | 优化后 | 证据范围 |
| --- | ---: | ---: | --- |
| 两个感知节点及其 TF 处理，合计单核 CPU | 156.08% | 2.14%，包含新网关 | 合成 19 个变换、50 Hz，各三轮至少 60 秒；没有推理与运动 |
| 腕部相机待机，单核 CPU | 42.26% | 1.11% | 同一相机、640×480、MJPG、配置 30 fps，各三轮至少 60 秒 |
| 未定位待机，整机平均 CPU | 历史 81.55% | 53.36% | 新版 60 秒实机样本；历史比较不是严格同工况三轮验收 |
| 新版未定位待机，最高滚动 10 秒 | — | 54.93% | 本次该工况低于 60% |
| 新版启动，最高滚动 10 秒 | — | 100.00% | 启动仍不满足目标 |

CPU 口径包含内核与硬软中断。单核 CPU 与六核整机 CPU 不能混用；单个进程的
60% 单核占用约为 10 个整机百分点。这里的核数归一化是忙碌时间统计，不代表各核
在不同频率下有相同的计算能力。

新相机三次重新订阅后，首张新鲜图像约 57–83 ms，5 秒收到 138–142 帧，
最大主机时间戳年龄约 51 ms。配置 30 fps 与交付约 28 fps 应分开报告。
主机采集时间戳不能证明硬件曝光时间，更不能据此保证 USB 缓冲中的图像绝对没有延迟。

控制线程已验证为 FIFO 50；这证明调度权限生效，尚不能证明所有控制周期都满足期限。
软件 ACT 测试覆盖完成、补帧、夹爪闭合输出与取消，仍不能代替实机夹持成功率。

## 3. 最值得保留的优化经验

### 3.1 先确认进程在做什么，再根据节点名称判断

物品识别和人员检测在没有图像、没有推理时仍然耗 CPU，主要线索是它们持续接收 TF。
关闭图像后仍高负载，一度容易让人继续怀疑模型或 Python 本身。

隔离回放把问题拆开：没有 TF 时节点基本空闲，加入高频 TF 后占用升高，停止 TF 后
再次降低。这个实验比根据进程名字直接换模型更有说服力。

可复用做法：对每个常驻进程列出输入话题、定时器、动作阶段和实际消费目的，
再用少量可控输入复现。先证明热点，后选择 C++、按需订阅或流程裁剪。

### 3.2 优化对象是数据流，包括发布端和订阅端

本次最有效的改变包括：集中消费 TF、让关节与里程计按阶段订阅、取消网页后台订阅、
相机在无人需要时省掉逐帧解码与大图发布。它们都减少了本来没有业务价值的处理。

同一份高频数据进入多个 Python 进程，会引入多个接收、反序列化和回调路径。
仅把缓存从十帧改为一帧，不能保证这些接收动作消失；仅降低某个诊断定时器频率，
也不能保证它订阅的大图流随之降低。

检查应贯穿采集、解码、发布、传输、接收、缓存和最终使用。需要按实际拓扑测量，
不能把消费者数量简单乘成实际复制次数或可回收 CPU。

### 3.3 C++ 的收益与减少工作量的收益要区分

共享网关同时改变了语言实现和重复消费次数；原生腕部驱动同时改变了语言、解码时机
和发布条件。因此本次结果不能概括成“所有 Python 改成 C++ 就能下降同样比例”。

任务编排和低频业务继续使用 Python。适合进入原生路径的是已证明高频、数据量大、
时序清楚且能单独测试的部分；全量重写会把性能问题扩展成行为兼容与维护问题。

### 3.4 真正的按需处理必须有完整生命周期

本次按需订阅包含：开始时清理旧状态、设置时间屏障、只收新数据、结束时销毁订阅，
以及拒绝上一代订阅尚未执行的回调。取消和异常必须走同一清理路径。

按需策略还改变了就绪条件：进程可用不等于当前动作已经拥有有效数据。寻人后退前
需要等新里程计；头部稳定判断仍需要完整关节流；ACT 不能使用 5 Hz 摘要驱动动作。
资源释放越积极，越要验证重入、断流、重连和取消后的下一次任务。

### 3.5 健康检查本身也可能是负载源

“为了知道相机在线而持续接收大图”是可以避免的工作。腕部已改由采集端发出低频健康信息，
外部健康节点不再需要腕部图像订阅。

这个经验在 D455 上尚未完全落实：当前健康节点仍接收头部彩色和对齐深度图。
后续如果改用采集端诊断，必须证明它反映的是相应数据流的新鲜度与有效性。
进程存活、设备已打开、心跳继续发送，都不能独立证明图像仍在更新。

### 3.6 功能裁剪要落到实际运行路径

隐藏按钮、默认关闭视频、设置“关闭工程功能”，不一定会销毁后端订阅和定时器。
这次精简网页同时关闭了地图、激光、路径、TF 和地图定时器，并拒绝对应 HTTP 入口。
维护姿态服务也退出正式 X1 启动链。

固定六条音频属于此前已完成的简化：它去掉动态物品名播报和运行时生成，降低播报链路
的不确定性。它应作为整体工程经验保留，但不能重复计入本次原生分支的新增 CPU 收益。
开放指令和开放物品目标仍保留，具体错误留在网页，不靠收窄任务能力掩盖资源不足。

### 3.7 参数、时序与控制契约比平均 CPU 更重要

保留图像原时间戳、指定时刻 TF、关节新鲜度、模型输入、动作队列和控制频率。
不能通过重新打时间戳、查询失败后改用最新 TF、减少控制采样或删除避碰步骤来得到好看的负载。
当前仍保持控制器 50 Hz、ACT 执行 30 Hz、Nav2 控制 20 Hz。

本机 ROS 参数覆盖曾出现“启动配置看似设置了，节点实际没有按预期生效”的问题。
经验是检查真实节点参数与实际 ROS 参数解析结果，不能只审查 YAML 文本。
实时权限同样需要检查实际线程的策略和优先级。

### 3.8 留下能推翻结论的证据

先保存原工作区与机器配置，再建立 `baseline/x1-pre-refactor` 和 `x1-native`。
源码、软件测试、局部基准、实机数据各自保留出处；机器地图、标定、录音、凭据和日志不提交。

本次也有验证中的教训：Humble 的诊断字节类型与整数比较导致测试脚本误判；
实际交付帧率低于配置帧率，暴露了测试中未经验证的假设。记录实际值、核查失败原因，
比修改断言直到变绿更重要。修改假设后仍需用预先明确的新鲜度、延迟和功能条件验收。

一次大进程跨包测试出现底层 `Bus error`，分包测试通过并没有证明该问题已修复。
它应保留在稳定性观察清单中。局部回放期间有少量开发负载，实机采样又同时运行了两个
观察进程；后续对照应收敛为单一采集器。不能把观察进程的 CPU 直接从结果中减去便宣称更低。

## 4. 后续优化的优先级

以下顺序以“先找影响演示成功的瓶颈，再付出更高改造成本”为原则。收益尚未实测，
不为每项预报可下降的百分点，也不把它们相加当成最终成绩。

| 优先级 | 工作 | 要回答的问题 | 代价或风险 |
| --- | --- | --- | --- |
| P0 | 任务阶段采样与稳定性验证 | 完整导航就绪及各任务阶段，哪个阶段真正超标、为何失败？ | 需要受控场景与实机时间，是后续决策依据 |
| P1 | 分组启动和错开模型初始化 | 能否让启动 10 秒窗口低于 60%，并保持可诊断、可取消？ | 启动可能变慢，必须处理依赖、超时和启动中途停止 |
| P1 | D455 健康诊断靠近采集端 | 能否消除仅为在线检查而产生的大图传输与对齐需求？ | 深度有效性、对齐、重连和健康状态需重新验证 |
| P1 | ACT 只在需要时取得观察图像 | 能否保留持续采集，减少任务中未使用帧的解码、传输和再次编码？ | 图像/关节配对、模型输入和动作队列可能受影响 |
| P2 | Nav2 组件组合及消息路径整理 | 多进程通信和执行器工作到底能减少多少？ | 生命周期、故障影响范围与控制延迟验证成本较高 |
| P2 | 语音与人员检测的阶段调度 | 重计算是否重叠，线程和预热是否造成峰值？ | 不能以转写变慢、漏唤醒、寻人不可靠为代价 |
| P3 | 内核、驱动、中断和调度局部优化 | 高系统态究竟由什么调用栈和设备路径产生？ | 需进一步采样，平台依赖强，回归面大 |
| 后续专题 | NPU 与减少远程 GPU 依赖 | 当前模型能否在端侧正确、高效运行？ | 属于新增端侧能力验证，不计入当前优化承诺 |

### P0：先把任务阶段与负载关联起来

下一次采样至少区分：启动、完整导航就绪待机、唤醒与转写、意图解析、定位/导航、
桌面识别与预抓取、ACT 执行、抓取验证、寻人、接近/递送、取消和终态播报。
阶段标记应来自任务事件与采样时钟，不能事后凭印象切分。

每个阶段同时记录整机 CPU、最高滚动 10 秒、用户态/系统态/中断、温度与频率，
以及有意义的功能指标：取帧等待和年龄、TF 失败、动作队列余量、控制超时、转写与播报延迟、
取消停止时间和任务结果。对于短于 60 秒的阶段，保留自然时长，重复多个任务；
不要人为停住动作凑满一分钟，并把它误当成正常执行负载。

对已知的定位失败、临近障碍物旋转失败、夹爪未闭合和递送失败单独分类：
现场/标定、模型输出、控制执行、消息时序、资源不足。只有证据吻合时才归因于 CPU。
先完成一轮端到端诊断，再把影响成功率或明显超标的阶段作为下一项优化对象。

### P1：分组启动，优先消除并发初始化峰值

2026-09-15 后续进展：已实现默认关闭的就绪驱动分组启动，并完成模拟流程验证；
同时减少性能采样自身的重复读取。详见[无人值守开发记录](x1-offline-validation.md)。
因用户不在现场，demo 已停止，分组启动尚无实机性能数据。

建议按依赖组织启动：先建立控制与停止路径，再启动必要传感器和状态入口，随后加载
导航及操作能力，最后错开语音与视觉模型初始化。精确分组应根据现有依赖图和启动日志确定。
对于必须预热的模型，安排受控预热，避免第一次任务把初始化开销全部补回来。

使用“依赖就绪且未超时”作为推进条件，少用固定 sleep 猜测设备启动速度。
中途失败不得宣布整个 demo 就绪，停止必须清理已经启动的子进程，不自动重启运动任务。
允许启动总时长适当增加，但必须报告它；不能把峰值移到用户第一次唤醒或抓取时。

### P1：图像路径继续从需求端追到源头

D455 先核对当前安装驱动的诊断、发布和对齐触发条件，再决定采用组合节点内健康监测
还是小范围驱动修改。只有证明颜色、深度和必要标定信息的新鲜度可替代当前检查，
才能撤掉健康节点的大图订阅。设备断流、无效深度、重连恢复都需要明确结果。

腕部现在在 ACT 动作期间仍向订阅者交付连续 BGR 图像，而参考配置的推理请求频率为
3 Hz。下一步可试验有期限的快照请求或原生选帧路径：相机持续取走新数据，按真实请求
提供观察。**3 Hz 推理请求不等于 30 Hz 动作执行**，不得因此降低执行频率。
HTTP 延迟、动作块补充和关节同步仍遵守现有契约。

直接复用相机 MJPEG 需要额外证明裁剪、缩放、颜色、压缩质量、时间戳与模型输入一致，
不能仅因省一次编解码就接入实机。保留原路径作离线输入和实机任务对照。

### P2：Nav2 组合值得试验，但先测通信成本

Humble 上游有组件组合启动路径，可作为适配参考；本项目仍须保留当前分阶段生命周期
和速度话题连接。建议先选相互通信多的原生组件试验，控制硬件与独立停止/碰撞路径保持隔离。
[Nav2 Humble 启动源码](https://github.com/ros-navigation/navigation2/blob/humble/nav2_bringup/launch/navigation_launch.py)

同进程运行不自动保证零复制，也不自动保证更好的尾部延迟。需要核对发布/订阅类型、
进程内通信配置、外部消费者和执行器阻塞情况，再看 CPU 与消息年龄是否共同改善。
[ROS 2 Humble 进程内通信示例](https://github.com/ros2/ros2_documentation/blob/humble/source/Tutorials/Demos/Intra-Process-Communication.rst)

物品定位、抓取验证和人员检测若已经在空闲时接近零 CPU，合并这些 Python 进程的
优先级应由活跃期数据决定。减少进程数量本身不构成收益证据，合并还可能引入推理阻塞竞争。

### P2：语音和人物检测先保持方案，检查实际并发

先沿用现有唤醒、Whisper、人员检测和固定 WAV，不立即切换模型。
核对任务期间暂停收音是否覆盖网页任务、终态播报后是否恢复，重计算是否按预期错开。
调整线程数前后比较实际延迟、识别结果和整机最高 10 秒负载，不能只比较进程平均 CPU。

本次语音待机约 9.22% 单核 CPU，不等于识别时只消耗这么多，也不是整机的 9.22%。
同样，人员检测节点的空闲下降不证明 YOLO 推理阶段已经低负载。

### P3：系统态与中断值得查，但不能先下结论

实测系统态 23.85% 与硬软中断 11.40%，合计约 35.25 个整机百分点，约占当时忙碌时间
的 66%。这提示后续必须观察内核侧开销；它不能直接证明 DDS、USB、某个相机或某个驱动
就是原因。该占比也不是“可全部回收的空间”或不可改变的系统下限。

先在可控窗口做进程/线程、调用栈、上下文切换和中断来源关联分析；比较消息传输、
设备采集、锁等待、调度唤醒与日志等实际路径。若需要更高开销的追踪，先做不运动的对照，
避免追踪工具本身制造超时。确认热点后再决定局部原生化、减少系统调用或调度调整。

IRQ 亲和性控制中断允许落在哪些 CPU，并不等于减少中断总工作量，而且依赖中断控制器
支持。因此不默认绑核或搬移 IRQ；有证据再对照总负载、控制周期和尾延迟。
[Linux 内核 IRQ 亲和性说明](https://docs.kernel.org/core-api/irq/irq-affinity.html)

本轮不通过统一 CPUQuota 压低数字，不优先换内核或 DDS，不削减控制频率、定位检查和碰撞监测。

## 5. NPU 专题与当前分支的关系

当前仍保持 Whisper、人员检测在 X1 CPU，ACT/VLM 使用原远程服务。用户提出的 NPU
部署方向保留为后续专题，不用尚未兑现的加速收益支撑当前 60% 目标。

建议先分别验证每种模型的导出、算子支持、数值/量化误差、端到端延迟、内存与 CPU
回退情况，再测共享 NPU 时的并发、排队和热稳态。不能根据标称算力或单模型演示，
推断 Whisper、人员检测、开放物品识别、意图识别和 ACT 可以一起稳定运行。

ACT 用于开放物品抓取的目标保持；模型部署成功不证明抓取泛化能力已经通过实机验证。
意图理解、桌面物品识别和抓取成功判断也须分别定义准确性与失败处理，再讨论 VLM 替代。
物品检测和意图理解仍需覆盖开放目标，不能悄悄改成固定类别和固定口令来达标。

继续在同一仓库的 `x1-native` 分支推进，不扩展成通用轻/重双产品框架。
公共动作契约、模型输入输出和机器配置边界值得保留；内部节点边界可以按 X1 实测调整。

## 6. 下一轮的交付与停止条件

建议下一轮交付“阶段负载与失败原因报告 + 一个有证据支持的优化 + 同工况回归”。
先做完整任务诊断与启动分组；图像、Nav2 或底层优化按诊断结果选择，不同时铺开多条高风险改造。

每次记录版本、参数引用、传感器配置、阶段、采样工具、开发负载、温度、前后数据和回退点。
主要可重复工况三轮各至少 60 秒；运动阶段按自然时长重复，最终完成原定的 30 分钟待机、
1 小时混合任务与至少 10 轮取物递送，并覆盖取消和受控故障恢复。

改动若增加旧帧、TF 失败、动作积压、控制超时或功能失败，应先回退或修复该改动；
不能用 CPU 均值下降抵消功能退化。未定位待机、完整就绪待机、启动和任务期分别判定，
不能用其中一个阶段的通过替代其他阶段。

达到既定负载、功能和稳定性目标后，保留经过验证的余量，停止收益不清楚的优化。
继续追求更低待机、NPU 离线化或新的感知能力时，应分别说明收益和成本，避免一直重构却没有
可重复演示的版本。

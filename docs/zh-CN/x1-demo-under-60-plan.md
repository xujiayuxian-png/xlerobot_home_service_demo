# X1 完整 Demo 低于 60% CPU 的重构方案

状态：已在 `x1-native` 分支开始实现，尚未通过整机验收。进度与实测见
[第一阶段实现记录](x1-native-implementation.md)。基于现有原生 Ubuntu 22.04 / ROS 2 Humble、
六个在线 CPU、既有地图和标定；ACT、VLM 继续使用现有远程服务。
下文的现状分析保留重构前的研究背景；当前结果和后续优先级请结合
[优化复盘](x1-optimization-retrospective.md) 阅读，不把原计划中的预期收益视作已实现收益。
本次检查时 demo 服务已停止，方案分析没有启动硬件或发起机器人动作。
讨论更新：本轮维持推理部署现状，Whisper 和人员检测继续在 X1 CPU，ACT/VLM
继续远程；NPU 迁移另做后续专题。独立 X1 分支已创建，迁移基线为 `bd85c8b`。

**1. 决策与验收口径**

新建专用于这台两轮机器人、以 ACT 抓取的 X1 正式运行配置。保留开放物品名称、
开放取物指令、目标定位、导航、抓取验证、寻人递送、唤醒与六条固定播报。
正式配置只加载这条演示链需要的代码；标定、数采、建图与工程观测使用独立启动入口。

核心决策是消除 Python 对高频机器人数据的重复消费，收拢图像处理，并按阶段安排
本地识别计算。本轮不通过新增远程推理依赖实现降载；NPU 的潜在收益不计入验收。
单纯降低日志量或把四线程改成两线程不再作为主要降载手段。

- CPU 口径：`/proc/stat` 计算全部六个在线核的整机忙碌时间，包含内核和中断。
  一个进程的 100% 单核 CPU 只相当于约 16.67 个整机百分点。
- 硬验收：启动、唤醒识别、导航、抓取、寻人递送及取消期间，每个连续 10 秒窗口
  的整机 CPU 均低于 60%。同时报告每秒峰值，不能用整场平均掩盖某个阶段超载。
  通用 Linux 的每个瞬时采样值都低于 60% 不作为可保证的实时性质。
- 工程预算按正常任务阶段不超过 50–55% 设计，预留至少 5–10 个百分点。
- 控制器 50 Hz、ACT 动作执行 30 Hz、Nav2 控制 20 Hz 保持；碰撞监测、
  定位门槛、夹爪实测闭合与持物验证保持。只减少非控制消费者的数据处理。
- 同时记录控制周期、图像年龄、动作队列、语音延迟、成功率和温度。
  低 CPU 但不能完成任务，判为不通过。

**2. 已有证据，以及上一轮为什么不够**

历史文件 `.xlerobot/environment/profile-20260915-082612.json` 的 60 秒整机平均为
81.55%，用户态以外的系统态约 30.05%，硬软中断合计约 13.30%。后两项已经包含在
整机总量中，不能再加一次。该次尚未初始定位，导航部分未激活，因此也不是完整
导航就绪后的性能验收成绩。

| 常驻进程 | 单核 CPU 平均 | 换算整机百分点 |
| --- | ---: | ---: |
| 物品识别节点 | 34.41% | 5.73 |
| 人员检测节点 | 33.08% | 5.51 |
| 任务节点 | 26.65% | 4.44 |
| 寻人编排节点 | 24.52% | 4.09 |
| ACT 适配器 | 24.30% | 4.05 |
| 腕部相机 | 20.27% | 3.38 |
| 网页后端 | 18.29% | 3.05 |
| 七项合计 | 181.52% | 30.25 |

物品识别和人员检测仍各有独立、常驻的 Python `TransformListener`；任务与 ACT
持续接收关节状态；寻人编排持续接收里程计。图像按需后，这些开销仍然存在。
历史隔离相机实验缺少完整平台的 TF/关节状态流，同类感知节点仅约 0.1% 单核 CPU。
两组不是严格单变量对照，不能把差值当成已经实现的优化收益。

本次另做了一次完全不连接设备的隔离回放：实际运行当前物品识别和人员检测两个
节点，后端关闭、图像按需、各四线程执行器。在独立 ROS 域发布合成 TF，每条包含
18 个关节变换及 odom→base_link，50 Hz。每段采样 20 秒：

| 微基准工况 | 物品识别节点，单核 CPU | 人员检测节点，单核 CPU |
| --- | ---: | ---: |
| 无 TF | 0.10% | 0.10% |
| 合成 TF 50 Hz | 69.88% | 72.13% |
| 停止 TF 后 | 0.05% | 0.05% |

这直接复现了没有图像、没有推理时的 TF 接收/执行器热点。合成拓扑和负载不同于
完整 demo，不能把其增量当成完整系统可回收的百分点；C++ 替代路径尚未测量。
原始结果与脚本在 `.xlerobot/environment/x1-under60-plan/`，临时进程已全部清理。

网页还有未裁干净的路径：`workspace=operator` 会订阅 `/map`、`/scan`、`/plan`，
运行 20 Hz 地图定时器；视频关闭和 `enable_engineering_tools=false` 并未关闭这些工作。

进程 CPU 之外仍有中断等开销，以上 30.25 个百分点不是可以直接全部减去的收益。
方案同时处理消息源头、消费次数和任务期峰值。

**3. 本轮五项工作**

| 重构 | 正式配置的明确行为 | 代价或验证要求 |
| --- | --- | --- |
| 单一 C++ 状态入口 | 为 demo 业务集中接收 TF、关节状态、里程计；Python 只接事件、低频摘要和请求的坐标快照 | 保留 Nav2/MoveIt 自身必需的原生数据订阅；坐标快照按图像时间查询，不能用旧变换代替 |
| 相机处理移入原生代码 | 腕部用 C++ V4L2 采集；最新帧有界缓存；没有消费者时不解码、不发布大图 | 设备保持打开并及时回收采集缓冲；对照颜色、JPEG 质量、帧序号及真实图像年龄 |
| 本地识别按阶段运行 | 保留本地唤醒、Whisper、人员检测和固定播放；ASR、人员检测、ACT 观察处理按任务阶段互斥 | 保留现有模型与部署，ASR 和人员检测的 CPU 峰值必须单独实测；既有按需推理不重复算新增收益 |
| 网页变为任务面板 | 只保留启动、取消、状态、文字错误；去掉正式模式的视频、地图、激光、路径和手动维护后台 | 失去运行期间的实时图像/地图观测；工程观测另开配置，不计入正式轻量演示 |
| 收缩本地 ROS 进程结构 | 物品识别、验证、人员检测改为单一请求工作进程内的函数；任务编排只消费事件；Nav2 原生组件组合 | 阻塞 HTTP 与控制执行器隔离，不能只把全部 Python 节点塞进同一个执行器 |

第一项具体替换位置是 `detect_object_node.py`、`scan_for_person_node.py` 的 TF 监听，
`fetch_deliver_task_node.py`、`act_policy_node.py` 的常驻高频关节回调，
以及 `person_search_node.py`、`operator_console.py` 的里程计或 TF 消费。
共享入口只服务本 demo，不建设新的通用机器人框架。

状态摘要供网页和任务调度使用，建议 2 Hz；安全和动作判断在原生路径执行，
每次动作开始需要新鲜状态快照。ACT 的腕图、六维关节状态和动作队列保持原有
时序契约，不使用 2 Hz 摘要驱动动作。非活动阶段不运行 ACT 观察处理。
保留现有动作合并、夹爪 governor 和本地流执行语义，避免把性能重构混成策略改动。

相机处理的重点是省去“每帧 MJPEG 解码→BGR 大图发布→跨进程搬运→选帧再编码”。
腕部继续请求 640×480、30 fps，采集线程持续取走最新数据；仅对推理实际选中的帧
执行必要解码和与现有接口一致的编码。15 fps 已出现新鲜度问题，本方案不采用它。
原始相机 JPEG 直接送模型需要独立验证，暂不把这项收益计入预算。

D455 保留 640×480、15 fps，采集与缓存使用原生路径；RGB-D 同步、对齐和快照
处理只在桌面识别、抓取验证或寻人阶段按需运行。相机健康信息在生产者一侧产生，
不再让一个额外的大图订阅仅仅用于证明相机在线。部署先验证现有驱动的组合与按需
处理能力；不能仅把诊断频率设为 2 Hz 就宣称底层图像处理也降到了 2 Hz。

Whisper 和人员检测继续在 X1 CPU 上运行，保持现有模型及输入处理；中文转写后仍走
现有远程意图解析。人物框结合本地同一帧深度、标定和变换计算位置。
结果带任务 ID、帧 ID 和期限，超时或取消后丢弃；人员移动后不得继续使用过期目标。
任务期间暂停听取新指令，也覆盖网页发起的任务；恢复收音必须等待任务及播报结束。
保持本地推理意味着原远程化方案中的语音/寻人预算须重新验证，不能沿用其预期收益。
若活跃阶段仍超标，继续处理本地前后处理、消息和调度热点，或明确记录目标未达成；
不擅自迁移模型，也不借未实施的 NPU 加速宣称达标。

Nav2 的控制、规划、行为、平滑等合适组件组合到原生进程中，保留目前的生命周期
激活顺序、频率和安全话题连接。控制硬件与独立停止/碰撞路径保留进程隔离，
HTTP、语音解码或模型计算不进入这些执行器。Humble 上游已有组合式启动实现；
这提供实现路径，但不保证本机某个固定的节省百分比。[Nav2 Humble 启动源码](https://github.com/ros-navigation/navigation2/blob/humble/nav2_bringup/launch/navigation_launch.py)

在支持的 C++ 内部图像路径使用进程内通信，减少复制和序列化；Python 图像消费者
全部退出后，不能再默认挂一个工程图像订阅破坏这条路径。ROS 官方演示说明了相关
条件，不意味着跨进程或 Python 路径会自动变成零复制。[ROS 2 Humble 进程内通信](https://github.com/ros2/ros2_documentation/blob/humble/source/Tutorials/Demos/Intra-Process-Communication.rst)

**4. 功能还在，但不再全部同时工作**

| 阶段 | 本地业务重处理 | 对外请求 | 整机设计预算 |
| --- | --- | --- | ---: |
| 分批启动与待机 | 必要平台、相机轻采集、唤醒、状态 | 低频健康检查 | ≤30% |
| 听取和理解 | 采音、本地 Whisper、播放固定提示 | 转写完成后意图解析 | ≤55%，须重测 |
| 自动定位与导航 | 激光、Nav2、定位质量和安全检查 | 无图像推理并发 | ≤50% |
| 桌面目标与预抓取 | 一次新鲜 RGB-D、投影与碰撞感知规划 | VLM | ≤50% |
| ACT 抓取与验证 | 腕部选帧、既有动作队列、本地执行和反馈 | ACT；动作结束后再验证 | ≤55% |
| 寻人、接近和递送 | 本地人员检测、分阶段定位/导航/递送执行 | 沿用既有必要远程能力 | ≤55%，须重测 |
| 取消和结束 | 取消子动作、确认停止、清理资源、固定播报 | 过期请求被丢弃 | <60% |

上述是分阶段的总预算，不是已经测得的结果，也不能把各行相加。
启动也按组串行进行，避免同时拉起几十个进程和模型造成 10 秒窗口超标。
任务期禁止视频编码、后台录包、模型预热并发；检测、规划、ACT、验证按状态机
顺序执行。寻人时的移动和观察保持安全的阶段切换，不牺牲取消响应。

保留后台导航生命周期，第一版不反复 deactivate/activate 全套 Nav2；消除机器人
业务节点的无用计算并做进程组合后再测导航本体。相机仍持续打开，第一版不靠
反复 USB 重启降低待机。预算若仍不满足，再针对采样证明的热点进一步改原生处理，
不能把“关掉定位/碰撞检查”当作通过验收的替代方案。

所有阶段进入前须确认：上个动作停止、资源所有者唯一、所需帧与状态新鲜、
子能力已经可接受请求。将就绪规则从“所有功能必须持续收到最新数据”改为
“能力可启动，当前阶段所需数据已经有效”；传感器故障仍报错，计划性休眠可区分。
HTTP、规划等耗时操作使用工作线程/进程和有界队列，取消与控制线程不等锁。

**5. 明确不作为主要收益来源的项目**

- MoveIt 目前承担 ACT 前的避碰 IK 和轨迹规划，保留必要能力。历史待机仅约
  1.02 个整机百分点，直接删除会破坏抓取，不能填补 21.55 个百分点以上的缺口。
  关闭多余可视化发布可以做，但不把它当成大收益。
- 正式界面固定 ACT，移除 centroid/GPD/SAM2 备用选项与无关启动检查。
  这些大模型原本在远端，不宣称删除它们能大幅降低 X1 CPU。
- 不启动维护预设服务；启动姿态完成证据交给状态入口后，初始化进程退出。
  这些是合理收缩，但收益较小。
- 左臂无关业务移出 demo；左侧总线还控制头部，不能整条关闭。
- 本轮不迁移 ACT/VLM 到 X1，不换模型，不更换内核或 DDS，也不寄希望于未实测的 NPU 加速。
- 不对整个 demo 设置 60% CPUQuota 来压低仪表数字。若给非控制工作进程限额，
  必须同时证明延迟和动作队列不退化；控制和安全线程不受这类限额约束。

**6. 实施顺序与停止条件**

1. 冻结当前版本与参数，补录真正导航就绪后的完整待机和各任务阶段基线。
   同时建立隔离的 TF/JointState 回放对照，以进程 CPU、整机 CPU、消息年龄和取消
   延迟验证热点，避免只凭节点名称重写。
2. 落实状态集中处理和真正的简版网页，释放所有非活动的高频订阅。
   第一关：完整待机降到 50% 以下；达不到就继续定位消息/执行器热点，不先开新功能。
3. 落实原生相机数据路径、单一视觉请求工作进程、本地识别的阶段调度。
   ACT 仍使用既有权重、动作语义和本地控制频率；旧新观察输入离线对照通过后接入。
4. 落实 Nav2 组件组合与阶段资源互斥，清除正式配置的备用/工程进程。
   第二关：任务各阶段目标 50–55%，全部 10 秒窗口低于 60%。未达标不标记完成。
5. 热稳态实机验收：完整待机 30 分钟，混合运行至少 1 小时，至少 10 轮取物递送，
   覆盖不同物品/摆放、取消、相机断流恢复和远程服务故障。真机故障测试先确保机器人
   可停且有人看护，不把软件压力测试直接注入运动控制。

每个主要修改在同工况做三次至少 60 秒对照。验收数据同时包含：每秒和滚动 10 秒 CPU、
最长执行超时、控制周期异常、ACT 图像年龄与队列最小余量、唤醒/理解结果、播报听感、
抓取/递送成功率、取消停止时间、进程残留和持续内存增长。

新增协议、资源切换和取消路径先通过不打开电机的最小测试；原来抓取闭合和定位
可靠性的问题单独跟踪。现有源码和公开动作接口尽量复用，拒绝通过降低成功率换 CPU。
配置放入忽略的 `config/local.yaml`，地图、标定、录音、日志、权重和凭据保持不提交。

这版方案接受的代价是：正式页面只显示任务信息，阶段之间可能多一次短等待，
需要维护少量新的 C++ 数据路径。本轮既有 GPU 依赖保持不变。
目标是用这些代价换取整个演示链的可验证 CPU 余量，保留实际取物递送能力。

**7. 建议采用独立 X1 分支，兼容范围限于必要契约**

开始实施前仓库在 `main`，有大量未提交的迁移、修复和优化修改。原 HEAD 并不完整
代表本机现状。现已保存源码基线 `baseline/x1-pre-refactor`，机器文件另做忽略目录备份；
不能从干净 HEAD 新建分支后误以为带上了当前有效修改，也不能直接提交全部工作区。

建议在同一仓库建立 `x1-native` 分支，允许它调整节点边界、C++/Python 分工、
启动结构和网页，不要求每一处改动同时适配原笔记本版本。原参考版本保持可复现；
当前迁移状态单独标记为性能未达标的基线，不能将其命名为已经验收的稳定版本。

暂不建设一个代码路径中大量 `light/heavy` 开关的双版本产品，也不复制成第二个仓库。
不同源码版本应隔离 build/install 和 Python 环境；若使用 worktree，部署入口要显式
选择目录，避免 X1 实机意外加载另一分支的 ROS overlay。

共同维护的边界只有：公开 tools 入口及 --hardware 门控、主要任务/能力动作契约、
标定与坐标单位、模型输入输出、取消/超时/安全语义。内部节点结构、部署脚本、
展示功能和平台依赖允许不同。通用缺陷修复挑选回合并；X1 架构改动无需强行回合并。
必要契约如确需改变，明确版本化并提供迁移说明，不静默破坏现有数据和服务。

X1 CPU 达标且实机验证通过后再记录里程碑，并从该基线分专题验证 NPU：
人员检测 → Whisper → 当前 ACT 权重 → 开放物品定位/意图与抓取验证。
这些是同一模型族的不同迁移问题，不假定一个导出流程覆盖全部。
普通固定类别物品检测不能代替开放词汇物品定位，也不能替代开放指令理解。

未来只在模型调用边界保留少量实现替换点：音频到文本、图像到人物框、开放描述到
目标定位、文本到结构化意图、观察到 ACT 动作块、抓取观察到验证结果。
目前不建设通用推理插件平台，也不实现未验证的 NPU 后端。
每项先验证正确性、实际算子落点、端到端延迟、CPU 残留、内存和热稳定性，
再验证分阶段共用 NPU。模型能分别运行，不代表并发或切换后仍满足控制时限。

# X1：官方运行时与完整 4B 模型实验

日期：2026-09-16。已完成离线验证和 demo 配置接入；随后首次实机测试出现
VLM 进程退出，尚不能认定整机验证通过。离线实验未打开电机。
前半部分保留首次实验过程；当前接入情况见“后续：离线验证通过，接入 demo 配置”。

## 目的

绕过现有 AidLux 4B 包，验证保留完整 Qwen3-VL 结构的另一条端侧路径。
此前偏框调查见 [诊断记录](x1-qwen3-vl-4b-diagnosis.md)。
新路径跑通也不能单独证明 DeepStack 是旧包问题的唯一原因：运行时、
权重量化和视觉处理均发生变化。

## 已验证的运行时准备

- 官方 `qai_hub_models_cli==0.62.2` 的模型清单没有 QCS8550 的现成
  Qwen3-VL-4B QAIRT 编译包，不能直接拿其他芯片的包替代。
- 官方 `geniex==0.6.1` 提供 Linux ARM64、GGUF 与 Hexagon 后端，
  安装包包含 `libggml-htp-v73.so`。
- 在原生 Ubuntu 22.04 上直接加载失败：缺少 `GLIBC_2.39` 和
  `GLIBCXX_3.4.32`。
- 将 Ubuntu 官方 libc6 2.39、libstdc++6/libgcc-s1 14.2 的 deb
  **解包到实验目录**，通过独立动态加载器运行实验 Python 后，
  可以枚举 HTP0；没有安装 deb、替换系统 libc、改系统服务或使用容器。
- 不只枚举：`backend_probe.py` 实际初始化并释放了 v73 DSP 会话，
  返回 4 个线程、4 个 HVX、1 个 HMX、8 MB VTCM。
  驱动的动态域查询失败后使用静态 CDSP 域，随后初始化成功。

DSP 初始化检查之后，完成了以下模型检测对照。

## 最小对照

使用官方模型清单指向的 `unsloth/Qwen3-VL-4B-Instruct-GGUF`：
Q4_0 主模型与 F16 视觉投影文件。固定选择 `llama_cpp:HTP0`，
CPU 辅助线程为 2，上下文 2048，输出上限 100 token。

采用与此前 GPU/厂商 NPU 对照相同的头部照片、双三次缩放 448×448、
PNG 和 0–1000 坐标提示，分别查找羽毛球与蓝色打火机。
检查原始输出、框位置、推理耗时及实际后端分配。
选择 HTP0 不等于保证每个算子都在 NPU，需以执行日志为准。

实验资源、模型、图片及日志全部位于忽略目录
`.xlerobot/npu/qwen3-official/`。`run-python` 只影响被启动的实验进程，
`backend_probe.py` 用于初始化检查，`probe.py` 用于两目标离线检测。
正式配置未切换到此路径。

## 实测结果

| 输入 | 羽毛球 | 蓝色打火机 |
|---|---|---|
| 相同 448×448 对照 | 找到，框 `[478,597,573,700]`，4.42 秒 | 未找到，2.68 秒 |
| 保留头部原图 640×480 | 找到，框 `[478,589,570,700]`，4.19 秒 | 找到，框 `[610,600,660,688]`，5.56 秒 |

坐标均为 0–1000。目视原图，原尺寸两框基本贴合目标；没有人为调整框。
448 对照的羽毛球框也明显优于旧包，但打火机仍漏检，因此不能声称
单靠更换运行时就解决了所有识别问题。这里只测了同一场景的两个目标，
不是任意物品准确率评测。

原尺寸这一轮加载 4.56 秒，视觉编码约 0.85 秒/图，生成约 11.2 token/s。
进程峰值 RSS 为 1,022,940 KiB；**不是整个模型总内存**，不包含全部
DSP/共享内存。一次加载加两次检测共 14.63 秒，进程 user+system CPU
时间合计 8.89 秒；没有据此推算完整 demo 的负载。

调试日志进一步确认：

- 主模型元数据 `qwen3vl.n_deepstack_layers=3`，视觉文件包含第
  5、11、17 层的 DeepStack 投影权重。
- 37/37 层被卸载到所选的 **HTP0**，其模型缓冲约 1955.75 MiB。
  llama.cpp 此处日志通用措辞为 `offloaded ... to GPU`，实际所选
  设备是 Hexagon NPU，不能据此理解成调用远程 GPU。
- 视觉编码器也选择 HTP0，但 UPSCALE 算子不受支持，存在 CPU
  协作。此实验是端侧 NPU+CPU，不能称为所有算子纯 NPU。
- 开启调试日志后复查一次羽毛球，框完全相同，耗时 4.17 秒。

首次连续调用中第二个请求报 `Multimodal generation failed`。
按独立检测任务在每次请求前调用 `model.reset()`，清理 KV 缓存和
采样器状态后，两次连续检测完成。后续服务接入必须保持请求串行与
会话隔离，不能直接复用未重置的状态。

另有退出时 HTP0 compute buffer 大小与预期不一致的提示，未阻断
本轮结果；尚未验证长期运行时是否有影响。原生 22.04 上仍需要这套
独立运行库，后续正式化应固定版本或重新构建兼容运行时。

## 首次实验结论（后续接入见下节）

**已跑通一条效果明显改善的 X1 端侧 4B 路径，值得继续；尚未迁移 demo。**
这一轮没有进行官方 QAIRT 模型重新导出，而是使用高通 GenieX 提供的
GGUF/Hexagon 路线，避免直接使用不支持本芯片的预编译资产。

下一步用少量现有图片补查空场景、其他小物体和腕部抓取判断，再接
OpenAI 兼容服务接口及意图解析。无需先展开大规模评测，但不能把
本次两个定位结果当成抓取验证、意图理解或完整递送已通过。

本地可视报告已更新，包含原图、模型原框及原始 JSON。
完成实验后推理进程已退出，demo 保持停止，现有生产配置未修改。

## 后续：离线验证通过，接入 demo 配置

同日完成小样本验证及常驻服务接入。当前机器配置已选择
`qwen3-vl-4b-instruct-geniex-q4_0-qcs8550`。此次没有启动 ROS 实机运动，
因此“已接入”指代码、配置、真实推理接口及联跑通过，不代表递送任务实机验收。

### 最终行为

- `services/npu/geniex_server.py` 在 `127.0.0.1:18888` 提供
  `/v1/models`、`/v1/chat/completions`、`/healthz`。
  意图、定位和抓取判断共用同一个常驻模型；每个请求重置会话，
  一次仅执行一个请求，忙时明确返回 503，不堆积推理。
- 请求仅接受内嵌图像，不下载 URL。保留相机原尺寸/比例，使用 PNG。
  输入限制为边长不超过 640、像素不超过 640×480；客户端只缩小超限图，
  不上采样。输出至多 192 token；截断结果保留 `finish_reason=length`，
  客户端拒绝将其当成完整结果。
- 抓取提示改为判断位置关系：夹爪口处被带起、桌面上且与夹爪口分离、
  无法看清。只把第一类判成功。沿用目标名称仅作辅助的思路，此视觉步骤
  判断“是否带起物体”，不是第二次核验物品类别。夹爪位置检查仍保留。
- 配套调整了 GenieX 的超时预算：单次腕部请求 15 秒，父级抓取验证
  35 秒，容纳既有的失败后新帧复核。此前父级只有 10 秒，可能在第二次
  视觉请求返回前就超时。其他模型的预算和机器人控制频率不变。
- 原来的 ACT、Whisper、人员检测模型、运行环境和接口保持原状。
  旧 AidLux VLM 包保留，但不会自动回退；GenieX 运行库仅进入 VLM 子进程。

### 小样本结果与实际客户端复测

| 类别 | 样本 | 最终结果 |
|---|---|---|
| 意图 | 拿蓝色打火机、递羽毛球、去桌面拿黄色胶棒 | 3 条均解析为正确物品，地点为 `table` |
| 非取物 | 不要拿了/取消、帮我拿那个 | 识别为 cancel/clarify；取物解析器拒绝发起任务 |
| 定位 | 头部羽毛球、蓝色打火机 | 2 个均找到，框基本贴合；约 6 秒/次 |
| 已抓起 | 历史腕部打火机、羽毛球 | 2 张均为 true，confidence=0.95 |
| 未抓起 | 桌面胶棒，两种朝向 | 2 张均为 false，confidence=0.75/0.85 |

最终通过 demo 的实际 Python 客户端复测上述 11 个样例，均符合预期。
取消/含糊样本的“通过”表示不会误发取物任务，不表示语音执行期间支持取消；
任务执行期间仍通过网页取消。已有语音简繁转换路径继续使用。

过程中保留了失败证据：JPEG 输入仍漏检小打火机；原先冗长的抓取提示
会将桌面胶棒判为成功，过度强调分离的短提示又会将正例判为失败。
最终位置关系提示在两正两负样本上通过，没有按文件名硬编码结果。
1280×960 上采样试验触发 `dspqueue_read failed: 0x0000002e` 并终止进程；
当前服务已限制尺寸，未启用这条不稳定路径。小样本通过不等于泛化问题已解决。

### 四服务共存与资源

公共入口 `tools/run npu --config config/local.yaml` 冷启动及停止验证通过。
四服务重启后同时发请求的结果：

| 调用 | 实测耗时 | 结果 |
|---|---:|---|
| 4B 检测打火机 | 6.13 秒 | 找到，原图框 `[388,282,422,334]` |
| ACT | 0.063 秒 | 返回有限的 100×6 动作数组，未下发执行 |
| 人员检测 | 0.085 秒 | 无人场景返回空列表 |
| Whisper | 1.25 秒 | 正确转写既有“拿桌上羽毛球”录音 |

单次并发只是共存检查，不是连续 ACT 控制回路或实际人员搜索效果评测。

四服务常驻、没有 ROS demo 的 20 秒待机采样：整机 CPU 平均 **10.84%**，
四服务及其管理进程合计约 **0.048%**（均以全部在线 CPU=100% 归一化）。
待机 HVX/HMX 为 0，QDSP6 平均约 0.64%。

另一段约 100 秒混合窗口（包含准备、客户端测试，开始阶段有构建工作）
整机 CPU 平均 16.63%，单秒峰值 35.87%，最大 10 秒均值 22.60%。
该窗口中 DSP 峰值 QDSP6/HVX/HMX 分别约 97.28%/87.20%/36.60%，
不能相加为单个 NPU 利用率。这些数字**不包含完整 ROS demo 常驻负载**。

### 部署、复现与回退

- VLM 独立依赖固定在 `services/npu/requirements-geniex.txt`，不要装进机器人
  或 ACT 的 Python 环境。当前使用 GenieX 0.6.1、Pillow 12.3.0。
- 忽略的 `service.json` 配置模型 ID、主模型、mmproj、Python、独立
  `runtime_root` 和 GenieX `library_dir` 的绝对路径。
  `tools/lib/geniex_runtime.py` 构造独立动态加载器命令；不替换系统库。
- 忽略的 `config/local.yaml` 引用 `npu.vlm_config`、`npu.manifest`。
  启动前核对模型、Python、独立运行库、GenieX 包和其他三个模型的 SHA256，
  本机清单覆盖 366 个去重文件。模型、录音和机器配置均不提交。
- `tools/run demo --hardware` 仍是实机入口。只测试推理时用 `tools/run npu`，
  完成后用 `tools/run npu --stop`，避免与实机 demo 管理进程争用。
- 原配置及工作区差异保存在 `.xlerobot/npu/qwen3-official/integration-before/`。
  停止服务后恢复该目录下的 `local.yaml` 可切回此前 AidLux 4B 配置；
  旧包已有识别缺陷，此操作不等于恢复到了效果已验收的版本。

本机验证数据位于 `.xlerobot/npu/qwen3-official/`：
`validation-results-initial.json`、`validation-image-ab.json`、
`validation-grasp-ab.json`、`validation-short-prompt.json`、
`validation-relations.json`、`service-results.json`、`coexistence.log`，
以及 `integration-resources/`、`idle-after/` 中的 CPU/DSP 逐秒记录。
小型软件测试覆盖串行执行、会话重置、临时文件清理、异常后拒绝继续推理、
输入尺寸约束、PNG/坐标映射及父子超时预算。未运行电机设备测试。

## 接入后首次实机失败（2026-09-16）

02:30:52 导航到达，02:30:56 转身完成，02:31:16 头部动作完成。
02:31:17 检测节点收到新 RGB-D 图像；02:31:18 本地 VLM 原生进程退出，
检测动作报后端错误，监督进程按既有策略停止整套 demo。这次失败不是
模型正常回答“未找到物体”。内核记录了禁用 core dump 的信息，原日志
没有子进程退出码，因此不能确定具体信号或原生调用栈。

该次记录中可用内存最低约 6.6 GiB，没有发现 OOM 证据。整机采样 CPU
平均约 62.5%、峰值 100%，包含启动和导航；此前约 10.8% 的推理待机值
不能代替整机运行数据。日志副本保存于本机忽略目录
`.xlerobot/incidents/20260916-geniex-crash/`。

关闭运动后，四模型并发、systemd 权限环境、相机开启及新鲜头部图像
重放均未复现原生退出。当前头部蓝色打火机仍出现过无效 JSON 或未检出，
属于另一个模型输出问题，不能据此解释原生崩溃。

服务层新增防护：模型加载、重置、推理、销毁固定在同一个常驻线程；
发布健康状态前完成一次 640×480 图像预热；记录请求开始/结束、原生故障
Python 栈及子进程退出码。这些是降低不确定性和补齐诊断的措施，
**尚未证明是原始崩溃的根治修复**。没有增加自动重启运动任务。

修改后保持相机开启，重跑 5 条意图、2 个物品检测、4 个抓取判断样本，
11 项均通过；四模型并发请求均返回，未执行 ACT 输出。图像请求约
5.9～6.8 秒。另有 5 项服务软件测试通过，包含跨请求调用线程时仍保持
原生模型生命周期同线程的检查。结果保存于上述故障目录的
`owner-thread-validation.log`；整机实测仍待完成。
